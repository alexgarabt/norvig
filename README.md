# Norvig Spell Corrector

A TypeScript implementation of Peter Norvig's probabilistic spelling corrector,
based on his 2007 essay
[How to Write a Spelling Corrector](https://norvig.com/spell-correct.html).

https://github.com/user-attachments/assets/b0a75920-c0ca-4f06-a350-d724828a6827

## Theory

### The objective

Given a (possibly misspelled) word $w$, we want to find the most probable
intended correction $c$:

$$\hat{c} = \underset{c \in C}{\arg\max} \; P(c \mid w)$$

### Applying Bayes' theorem

By Bayes' theorem:

$$P(c \mid w) = \frac{P(w \mid c) \cdot P(c)}{P(w)}$$

Since $P(w)$ is constant across all candidates $c$, it can be dropped:

$$\hat{c} = \underset{c \in C}{\arg\max} \; P(c) \cdot P(w \mid c)$$

This decomposes the problem into three components:

**Language model** $P(c)$ -- the prior probability that word $c$ appears in
text. Estimated by maximum likelihood from a corpus:

$$P(c) = \frac{\text{count}(c)}{N}$$

where $N$ is the total number of tokens in the corpus.

**Error model** $P(w \mid c)$ -- the probability that, intending to write $c$,
the user produces $w$. Norvig simplifies this to a priority hierarchy: all
known words at edit distance 1 are treated as equally probable, and infinitely
more probable than known words at edit distance 2. Formally:

$$P(w \mid c) \propto \begin{cases} \infty & \text{if } d(w, c) = 0 \text{ and } c \in D \\ 1 & \text{if } d(w, c) = 1 \text{ and } c \in D \\ \epsilon & \text{if } d(w, c) = 2 \text{ and } c \in D \\ 0 & \text{if } d(w, c) > 2 \end{cases}$$

Because all candidates within the same edit distance share the same
$P(w \mid c)$, this factor cancels out and the selection reduces to:

$$\hat{c} = \underset{c \in C_k}{\arg\max} \; P(c)$$

where $C_k$ is the first non-empty priority level:

$$C_k = \begin{cases} \{w\} & \text{if } w \in D \\ \{c \in D : d(w, c) = 1\} & \text{if the above is empty} \\ \{c \in D : d(w, c) = 2\} & \text{if the above is empty} \\ \{w\} & \text{fallback} \end{cases}$$

**Candidate model** $C$ -- the set of words to consider. Instead of computing
edit distance from $w$ against every word in the dictionary $D$ (brute force),
Norvig inverts the problem: generate all strings within edit distance 1 of $w$,
then check which ones exist in $D$ (stored in a hash set for $O(1)$ lookup).

### Candidate generation

Let $\Sigma$ be the alphabet with $|\Sigma| = a$ (26 for English). For a word
$w$ of length $n$, define:

$$\text{edits}_1(w) = \text{Del}(w) \cup \text{Trans}(w) \cup \text{Sub}(w) \cup \text{Ins}(w)$$

where:

$$\text{Del}(w) = \lbrace w_1 \dots w_{i-1} \cdot w_{i+1} \dots w_n : 1 \le i \le n \rbrace, \quad |\text{Del}| = n$$

$$\text{Trans}(w) = \lbrace w_1 \dots w_{i+1} \cdot w_i \cdot w_{i+2} \dots w_n : 1 \le i \le n-1 \rbrace, \quad |\text{Trans}| = n - 1$$

$$\text{Sub}(w) = \lbrace w_1 \dots w_{i-1} \cdot \sigma \cdot w_{i+1} \dots w_n : 1 \le i \le n,\; \sigma \in \Sigma,\; \sigma \ne w_i \rbrace, \quad |\text{Sub}| = n(a - 1)$$

$$\text{Ins}(w) = \lbrace w_1 \dots w_{i-1} \cdot \sigma \cdot w_i \dots w_n : 0 \le i \le n,\; \sigma \in \Sigma \rbrace, \quad |\text{Ins}| = (n + 1) \cdot a$$

Total candidates before deduplication: $54n + 25$ (for $a = 26$).

Candidates at edit distance 2 are generated by composing edits:

$$\text{edits}_2(w) = \bigcup_{e \in \text{edits}_1(w)} \text{edits}_1(e)$$

The known candidates at each level are:

$$\text{known}_k(w) = \text{edits}_k(w) \cap D$$

## Complexity analysis

Let $n$ = word length, $a = |\Sigma|$ (alphabet size), $|D|$ = dictionary size,
$\bar{m}$ = average word length in $D$.

### Time complexity

**Edit distance 1 generation and lookup:**

Generating each candidate string costs $O(n)$ (slicing and concatenation). There
are $O(a \cdot n)$ candidates. Looking up each in the hash set costs $O(n)$
(hashing). Total:

$$T_1 = O(a \cdot n^2)$$

For $n \approx 7$, $a = 26$: a few thousand operations. Essentially instant.

**Edit distance 2:**

We apply the inner edit loop to each of the $O(a \cdot n)$ unfiltered results
from edits1:

$$T_2 = O(a^2 \cdot n^3)$$

In practice, for a typical English word this produces ~90,000 intermediate
strings. Still milliseconds.

**Comparison with brute force** (computing Wagner-Fischer against every
dictionary word):

$$T_{\text{brute}} = O(|D| \cdot n \cdot \bar{m})$$

With $|D| \approx 300{,}000$ this is orders of magnitude slower.

### Space complexity

$$S = O(|D| \cdot \bar{m}) + O(a \cdot n^2)$$

Dominated by the dictionary. For Norvig's corpus (~32k words, ~1.1M tokens)
this is roughly 225 KB.

The edits2 step is implemented inline: the second-level candidates are checked
against the dictionary as they are generated, so the ~160,000 intermediate
strings from edits2 are never materialized into a collection. Only the (few)
known matches are stored.

## Implementation

### `norvig.ts`

The `Norvig` class loads a plain-text corpus, tokenizes it, and builds a
word frequency map (`Map<string, number>`). It exposes:

- `candidates(word)` -- returns the first non-empty candidate set following
  the priority hierarchy (distance 0 > 1 > 2 > fallback).
- `probability(word)` -- unigram probability $P(w) = \text{count}(w) / N$.
- `correction(word)` -- returns the single most probable correction.
- `correction(word, n)` -- returns the top $n$ corrections with probabilities.

There are three internal generation methods:

- `edits1(word)` -- generates all strings at distance 1, unfiltered. Used as
  the intermediate step for edits2.
- `knownEdits1(word)` -- generates distance-1 edits and filters against the
  dictionary inline. No intermediate set of non-words is materialized.
- `knownEdits2(word)` -- iterates over `edits1(word)`, then for each result
  applies the edit operations again, checking each candidate against the
  dictionary inline to avoid storing ~160k strings.

### Usage

```typescript
import { Norvig } from './index.js';

const spell = new Norvig({ corpus: './big.txt' });

spell.correction('speling');          // 'spelling'
spell.correction('korrectud');        // 'corrected'

spell.correction('somthing', 3);
// [
//   { word: 'something', probability: 0.000223 },
//   { word: 'soothing',  probability: 0.000011 },
//   { word: 'smoothing', probability: 0.000005 }
// ]

spell.candidates('graffe');           // Set { 'giraffe', 'gaffe', ... }
spell.probability('the');             // ~0.0715
```

The corpus file should be a plain text file. Norvig's original
[big.txt](https://norvig.com/big.txt) (~6 MB, ~1.1M tokens, ~32k unique words)
is a concatenation of public domain texts from Project Gutenberg and word
frequency lists from Wiktionary and the British National Corpus.

## Known limitations

1. **Uniform error model.** All edits at the same distance are treated as
   equally likely. In reality, substituting adjacent keyboard keys (e.g. "a"
   for "s") is far more probable than distant keys. Kernighan et al. (1990)
   used confusion matrices trained on real error data to model this.

2. **No context.** The corrector examines one word at a time. It cannot know
   that "where" should be "were" in "They where going". Norvig estimates that
   reaching 90% accuracy requires using surrounding word context.

3. **Unknown words.** If the correct word is not in the corpus, there is no
   way to suggest it. In Norvig's final test set, 11% of expected corrections
   were absent from the dictionary.

4. **Alphabet-dependent.** Candidate generation scales with alphabet size. For
   languages with large character sets (e.g. Chinese with ~70,000 Han
   characters), the number of candidates at distance 1 becomes impractical.
